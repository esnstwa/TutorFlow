# Архитектура TutorFlow

## Назначение

TutorFlow — веб-платформа для взаимодействия частных репетиторов и учеников. Первая версия должна упростить установление связи между участниками, а последующие этапы — поддержать расписание, учебные задания, сдачу работ, файлы, комментарии, статусы и историю обучения.

## Роли и основной сценарий

- `TUTOR` — репетитор.
- `STUDENT` — ученик.

Основной сценарий первой версии:

1. Репетитор создаёт уникальную ссылку-приглашение.
2. Ученик регистрируется по этой ссылке.
3. Между аккаунтами создаётся связь.
4. Репетитор и ученик отображаются в личных кабинетах друг друга.

## Архитектурный подход

Проект разрабатывается как **модульный монолит**: единое приложение и единая кодовая база разделяются на предметные модули с явными зонами ответственности. Такое решение упрощает разработку и развёртывание первой версии, сохраняя границы для дальнейшего развития системы.

Предполагаемые backend-модули:

- `core` — общая конфигурация и базовые инфраструктурные механизмы;
- `auth` — аутентификация и авторизация;
- `users` — учётные записи и роли пользователей;
- `invitations` — ссылки-приглашения и их жизненный цикл;
- `students` — связи репетиторов с учениками;
- `lessons` — расписание и занятия;
- `assignments` — домашние задания;
- `submissions` — сдача и проверка работ;
- `comments` — обсуждение учебных материалов и работ;
- `notifications` — уведомления пользователей.

Состав модулей и их внутреннее устройство уточняются на этапах реализации. Пустые директории заранее не создаются.

## Технологический стек

- Python и FastAPI;
- PostgreSQL;
- SQLAlchemy 2.x и Alembic;
- Jinja2, HTML, CSS и JavaScript;
- Redis и Celery для будущих фоновых задач;
- Docker и Docker Compose;
- pytest;
- Locust.

React не используется. Сервер формирует страницы через Jinja2, а клиентская часть строится на HTML, CSS и JavaScript.

## Инфраструктура

Основные инфраструктурные компоненты: PostgreSQL для постоянного хранения данных, Docker и Docker Compose для воспроизводимого окружения, pytest для автоматизированного тестирования и Locust для нагрузочного тестирования.

Redis и Celery подключаются только на соответствующем этапе, когда в проекте появятся реальные фоновые задачи. До этого их конфигурация и реализация не добавляются.

## Ответственность участников

### Исаков Артем — основной backend

- архитектура приложения;
- FastAPI и серверная часть;
- PostgreSQL, SQLAlchemy и Alembic;
- бизнес-логика;
- аутентификация, авторизация и права доступа;
- будущее подключение Redis и Celery;
- тестирование;
- Docker;
- нагрузочное тестирование и оптимизация.

### Иванова Ксения — дизайн и frontend

- UI/UX;
- Jinja2-шаблоны;
- HTML, CSS и JavaScript;
- адаптивность;
- визуальные компоненты;
- проработка пользовательских сценариев.

Бизнес-логика и все проверки прав доступа выполняются на backend. Клиентский интерфейс не считается доверенной границей и не должен быть единственным местом проверки правил.

## Подход к разработке

Разработка ведётся небольшими независимыми этапами. Каждый этап должен иметь ограниченный объём, понятный результат и собственную проверку. Новые модули и инфраструктурные компоненты добавляются только тогда, когда они требуются текущим пользовательским сценарием, без преждевременной реализации будущих возможностей.
