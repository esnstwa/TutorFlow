## Выбор модуля и Р1 — ответственность

Выбран календарный read-model, ранее реализованный точкой `app.services.calendar_events`. Он подходит для ПЗ №2: это существующая операция, вызываемая страницей расписания и API уроков, объединяющая содержательное формирование календарных событий с чтением ORM и представлением HTTP/UI. Её можно выделить, не меняя маршруты и пользовательский формат.

Цепочка ответственности:

> FR-07 (созданное занятие отображается в календаре после повторной загрузки) → нейтрально спроецировать календарь преподавателя; уже существующие маркеры проверки отправленных работ сохранить как совместимое поведение, а не как новое правило FR-07 → `CalendarEventService.list_events(teacher_id, date_from, date_to)` → прикладная точка `app.services.calendar_events(...)` → обработчик страницы расписания и endpoint списка уроков в `app.web.router`.

FR-07 взят из [`docs/mdk03.02/pz01/REQUIREMENTS.md`](../../../mdk03.02/pz01/REQUIREMENTS.md) и применяется здесь только к отображению сохранённого занятия. Маркеры проверки домашней работы оставлены лишь потому, что они присутствовали в прежнем read-model; их бизнес-политика этим изменением не расширяется. `CalendarEventService` отвечает за нейтральную проекцию записей и временные интервалы. Источник отвечает за выборку; `app.services.calendar_events` связывает реализацию и сохраняет прежний формат представления; HTTP-маршрут отвечает за HTTP-вход/выход и авторизацию. Ядро расписания не импортирует HTTP, SQLAlchemy, ORM-модели или шаблоны. Схема импортов приведена в [`docs/module-map.md`](../../../module-map.md).

## Р2 — контракт публичной операции

Публичная операция — `CalendarEventService.list_events(...)`. Документация по стандарту Python docstring и пример вызова находятся в `app/schedule/calendar.py`.

| Часть | Контракт |
|---|---|
| Вход | `teacher_id: int` используется для области выборки; существование преподавателя отдельно на этой границе не проверяется. Необязательные `date_from` и `date_to` типа `date` ограничивают календарные уроки по локальной дате начала; обе границы включены. Диапазон не нормализуется и не валидируется. |
| Результат | Новые нейтральные `CalendarEvent` в порядке: уроки по `start_at`, затем сданные работы в порядке источника. Урок содержит идентификатор, локализованные начало/окончание, статус и непрозрачный снимок подробностей. Событие проверки — идентификатор получателя и часовой интервал. HTTP-поля в этом результате отсутствуют. |
| Включение данных | Источник включает все статусы урока (в том числе `cancelled`), потому что текущая календарная выборка их не исключает. События сданных работ выбираются по статусу `SUBMITTED` и не фильтруются по диапазону дат — это существующее поведение. |
| Время | Времена с часовым поясом переводятся в `Europe/Moscow`; naive `datetime` трактуется как московское время, как в существующем коде. |
| Ошибки и порядок | Сначала вызывается `lessons_for_teacher`, затем строятся уроки, затем вызывается `submissions_for_teacher`, затем формируются события проверки. Исключение чтения уроков прекращает вызов до чтения сдач; исключения источника не перехватываются и не переводятся. Некорректный снимок с `SUBMITTED` и `submitted_at=None` передаёт существующий `AttributeError` из локализации. При `date_from > date_to` оба имеющихся источника возвращают пустой набор уроков; события проверок остаются неотфильтрованными. |
| Владение | Dataclass-событие неизменяемо по присваиванию полей; вложенная карта деталей — снимок. Поставщики возвращают данные, которыми владеет вызывающий код. In-memory поставщик копирует данные при создании и чтении; SQL-адаптер сериализует новые детали на каждый запрос. |
| Побочные эффекты | Потребитель не меняет входные снимки и сам не инициирует сохранение. Оба SQLAlchemy-чтения, включая текущий read-only `lesson_dict`, выполняются в `session.no_autoflush`: это подавляет лишь неявный autoflush в этой области, но не явный `flush` и не произвольные побочные эффекты serializer. Адаптер сам не вызывает `flush`, `commit`, `rollback` или `close`; сессией владеет вызывающий код. |
| Не входит в контракт | Проверка HTTP-доступа, создание/перенос занятий, правила конфликтов, транзакционное бронирование и продуктовая политика статусов. Пересечения, отмена, касание границ и конкурентные изменения не переопределяются этой работой. |

Пример использования:

```python
source = InMemoryCalendarEventSource(lessons=[], submissions=[])
events = CalendarEventService(source).list_events(teacher_id=12)
assert events == []
```

## Р3 — реализация и интеграция

Реализованы `app/schedule/calendar.py` и `app/schedule/sqlalchemy_source.py`. Содержательная проекция вынесена в storage-independent сервис. Существующая `calendar_events(...)` остаётся совместимой точкой сборки и адаптером старой формы ответа, поэтому два текущих HTTP-потребителя продолжают вызывать её без изменения маршрутов.

Интеграция проверена локальными тестами расписания. PR, merge и immutable tag не выполнялись: пользователь прямо ограничил работу локальной веткой. Поэтому критерий регламента слияния не заявляется выполненным.

## Р4 — подмена реализации

| Реализация | Назначение | Ограничение |
|---|---|---|
| `SQLAlchemyCalendarEventSource` | Production-подключение к SQLAlchemy session через точку сборки `app.services.calendar_events` | Parity-тесты используют SQLite; отдельно rollback-only smoke чтения через SQLAlchemy source прошёл на изолированном PostgreSQL 16. Это не доказывает полную PostgreSQL parity, production auth, план запроса или конкурентность; сессией владеет вызывающий код. |
