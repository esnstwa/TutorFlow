# ADR-002 — выделение контракта проверки пароля

- **Статус:** принято для ПЗ №2; проверка и публикация ещё не завершены.
- **Автор:** Ксения Иванова.
- **Дата решения:** 19.10.2026.
- **Область:** регистрация и авторизация TutorFlow.

## Контекст

До выделения границы маршрут `app.auth.router.login` напрямую вызывал функцию `verify_password`. HTTP-потребитель знал о конкретном способе проверки и отдельно обрабатывал исключение непригодного Argon2-хэша. Для ПЗ №2 нужна существующая бизнес-логика с полным поведением, документированным контрактом и возможностью проверить потребитель с другой реализацией без переписывания маршрута.

Ограничения: сохранить общий ответ 401 для неуспешной аутентификации, не раскрывать хэши и пароли, не дублировать настройки TTL из PR #15, не вводить новый внешний сервис или продуктовый сценарий.

## Рассмотренные варианты

1. **Оставить прямой вызов `verify_password`.** Минимум изменений, но граница зависимости не выражена, а подмена потребителя требует monkeypatch внутренней функции.
2. **Выделить весь HTTP-модуль регистрации/входа.** Контракт получается широким и смешивает JSON, БД, сессии, CSRF и парольную проверку; подмена потребовала бы изолировать слишком много инфраструктуры.
3. **Выделить `PasswordVerifier` и передавать его через FastAPI dependency injection.** Граница содержит одну бизнес-операцию, production-реализация сохраняет Argon2, тестовая реализация подключается к тому же `login` без изменения его кода.

## Решение

Выбран вариант 3:

- публичный контракт — `PasswordVerifier.verify(password, password_hash) -> bool`;
- production-реализация — `Argon2PasswordVerifier`;
- точка сборки — `get_password_verifier`;
- потребитель — `app.auth.router.login`;
- тестовая взаимозаменяемая реализация — `tests.support.passwords.FixedPasswordVerifier` через `app.dependency_overrides`.

## Последствия

### Положительные

- маршрут не зависит от Argon2 и не переписывается при тестовой подмене;
- ошибки непригодного хэша имеют единый безопасный результат `False`;
- контракт можно проверять отдельно и через реальный HTTP-путь;
- существующий `core.security.verify_password` сохраняется как совместимый фасад;
- граница даёт отдельный модуль-кандидат для будущего измерения.

### Цена решения и ограничения

- добавлен публичный тип-контракт и ещё одна точка DI;
- появился дополнительный косвенный вызов от `login` к провайдеру;
- тестовая подмена не проверяет Argon2, БД и реальные хэши;
- production-проверка всё ещё зависит от параметров Argon2 и вычислительной стоимости, поэтому нагрузочный вывод отложен до измерений;
- `PasswordVerifier` проверяет только пароль против хэша, а не нормализацию email, состояние пользователя или создание сессии.

## Проверка решения

1. Запустить `tests/test_auth_module_contract.py` с двумя реализациями.
2. Проверить существующие auth-тесты на регистрацию, вход, сессии и повреждённые хэши.
3. Сверить импорты и карту `docs/architecture.md`.
4. Перед публикацией передать зафиксированный commit другому студенту для Р7; независимый проверяющий должен повторить команды и проверить подмену.
5. В последующей работе измерить время `Argon2PasswordVerifier.verify` на воспроизводимом наборе входов; до этого не объявлять узкое место.
