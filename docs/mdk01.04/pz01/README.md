## Границы технической части

Самостоятельный вклад для зоны расписания — поставка `schedule.html` и `schedule.css` в wheel с проверкой состава. Общая часть каркаса — runtime-диагностика версии/SHA, безопасные события запуска/остановки, проверка конфигурации, совместимый `/health` и содержательная CI-проверка. `/health` сохраняет ответ `{"status":"ok"}` и не запускает диагностику/Git на каждый запрос. Бизнес-логика расписания, авторизация и UI в рамках этой доработки не менялись.

Wheel — артефакт минимального воспроизводимого smoke-сценария, а не отдельная микрослужба или миграционный пакет. В него попадают отслеживаемый код `app/`, необходимые шаблоны и статические ресурсы, а также `build-info.json`; корневые миграции, тесты, документация и неотслеживаемые локальные файлы не копируются. Сценарий проверяет запуск приложения, `/health` и CSS без подключения к БД, поэтому миграции для него не требуются.

## Статус критериев Р1–Р7

| Критерий | Статус | Подтверждение / оставшаяся граница |
|---|---|---|
| Р1 — обоснование и инструменты | Готово | ADR-001 и декларация семи инструментов в TOOLCHAIN. |
| Р2 — собственная часть каркаса | Готово локально | Сборщик проверяет шаблон/CSS расписания; тест подтверждает, что неотслеживаемые файлы приложения не попадают в staging. |
| Р3 — конфигурация, версия/SHA, диагностика | Готово локально | Проверяются штатная и ошибочная конфигурации, безопасный вывод, короткие SHA и выбор источника. |
| Р4 — путь исполнения | Готово локально | Цепочка от lock-файла и wheel до CPython/Uvicorn/FastAPI описана и проверяется командами из RUNBOOK. |
| Р5 — два режима запуска | Готово для smoke-сценария | Один и тот же запрос `/health` и CSS проверяется в source checkout и установленном wheel вне checkout. Это не сравнение производительности и не Docker-проверка. |
| Р6 — независимое воспроизведение | Не выполнено | Нужен запуск другим студентом в чистом окружении и заполненный протокол; авторская/автоматическая проверка его не заменяет. |
| Р7 — содержательная CI-проверка | Реализация готова; итог привязан к HEAD PR | Quality Gate сравнивает результат компонента с независимым `git rev-parse HEAD`, удаляет подменяющие env vars и содержит отрицательную проверку. Состояние Actions смотреть для точного HEAD PR. |

## Доказательства и ограничения

Фактические локальные результаты и команды приведены в [EVIDENCE.md](EVIDENCE.md). Скриншоты 1–7 в комплекте не подменены текстом или заглушками: карта указывает, какие подлинные изображения ещё нужно приложить. Р6 и рисунок 6 остаются незакрытыми до проверки другим студентом. Предыдущее решение ревьюера `CHANGES_REQUESTED` не считается снятым автоматически — повторное решение должно появиться в PR после проверки нового HEAD.
