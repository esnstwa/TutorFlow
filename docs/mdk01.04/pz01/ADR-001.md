# ADR-001 — выбор стека TutorFlow

- **Статус:** принято; документ фиксирует фактически используемую архитектуру.
- **Автор:** Исаков Артём.
- **Дата:** 16.10.2026.

## Контекст

TutorFlow — веб-платформа для частных репетиторов и учеников. Основные сценарии включают регистрацию и авторизацию, кабинеты, расписание и учебные материалы. Проект развивается небольшим студенческим коллективом; индивидуальная зона автора этого изменения — расписание. На момент решения в репозитории уже есть Python-приложение, HTML-шаблоны и JavaScript, тесты, миграции PostgreSQL и CI.

Ограничения: не вводить инфраструктуру без реальной функции; сохранять модульный монолит; запускать сервис локально и в контейнере; не раскрывать настройки подключения и другие секреты в диагностике; поддерживать повторную установку прямых и транзитивных зависимостей.

## Решение

- **Язык и среда:** Python, минимально поддерживаемая версия — 3.12; контейнер и CI используют ветку Python 3.12.
- **HTTP-приложение:** FastAPI под ASGI-сервером Uvicorn. Модель исполнения — обработка HTTP-запросов/ответов через ASGI; приложение не создаёт собственные фоновые потоки и не требует параллелизма для текущего сценария.
- **Хранение данных:** PostgreSQL, SQLAlchemy 2.x и Alembic.
- **Представление:** Jinja2, HTML, CSS и JavaScript; отдельный frontend bundler не требуется.
- **Поставка и зависимости:** setuptools собирает wheel; версии Python-пакетов закрепляет `uv.lock`, синхронизация выполняется с `uv sync --locked`. Docker использует тот же lock-файл.
- **Проверка:** pytest; текущая CI-последовательность также компилирует Python-модули, запускает JavaScript-тесты и проверяет миграции.

## Рассмотренные альтернативы

| Альтернатива | Причина отказа |
|---|---|
| Django | Даёт встроенные ORM, admin и auth, но переход с уже работающего FastAPI потребовал бы замены существующих маршрутов и интеграций без необходимой для текущих сценариев выгоды. |
| Flask | Подходит для небольшого сервиса, но проект уже использует модели запросов, валидацию и ASGI-совместимый стек FastAPI; смена сейчас добавила бы миграцию вместо функции. |
| Node.js + SPA-фреймворк | Потребовал бы отдельного клиентского build-контура, хотя текущий интерфейс уже серверный на Jinja2 и дополняется JavaScript. |
| Redis и Celery | Не выбраны для текущей реализации: фоновые задачи пока не являются необходимостью продуктового сценария. Архитектурный документ допускает их подключение позднее. |

## Последствия

**Положительные:** единая кодовая база; существующий код и текущие навыки команды переиспользуются; серверная валидация и шаблоны работают в одном приложении; PostgreSQL и миграции покрывают постоянное хранение; контейнерный и локальный пути используют один исходный компонент.

**Ограничения и обязательства:** Python остаётся интерпретируемой средой, поэтому release не является native executable; режимы сравниваются по способу подготовки и размещению пакета, а не по недоказанной производительности. Поставочный wheel должен включать шаблоны и статические ресурсы. Версии зависимостей нельзя устанавливать только по диапазонам из `pyproject.toml` — требуется lock-файл и `--locked`. Диагностика не должна выводить `DATABASE_URL`, пароли, токены или содержимое `.env`. Статический `compileall` проверяет синтаксис, но не заменяет типизацию и линтер; Ruff пока не подключён.

## Проверка решения

- `uv sync --locked --extra dev` устанавливает версии из lock-файла.
- `python scripts/check_component.py` проверяет запуск, конфигурацию, версию и SHA.
- `python scripts/build_component.py wheel --out-dir <вне-репозитория> --work-dir <вне-репозитория>` формирует wheel с данными сборки и проверяет состав.
- Различия режимов фиксируются фактическим запуском одного сценария из checkout и установленного wheel вне checkout; сравнение скорости не проводится.
