# Постоянное хранилище материалов

## Размещение и перезапуск

Приложение использует существующий `FILE_STORAGE_PATH` (по умолчанию `var/uploads`). Путь должен быть приватным каталогом приложения, вне `app/web/static`, без symlink/junction и переходов `..`. Содержимое не публикуется статическим сервером; выдача идёт только через авторизованный API.

В `docker-compose.yml` для `web` настроены:

- `FILE_STORAGE_PATH=/app/var/uploads`;
- отдельный named volume `material_data:/app/var/uploads`;
- `FILE_UPLOAD_MAX_BYTES`, по умолчанию `20971520` (20 MiB), допустимо только уменьшение.

Путь внутри контейнера остаётся постоянным. Обычный перезапуск процесса или пересоздание контейнера с тем же volume не должен менять содержимое. Удаление volume или запуск другого Compose project с пустым volume — другая операция, не эквивалентная перезапуску. Не выполнять `docker compose down -v` для рабочего развёртывания.

Изменение Compose-конфигурации само по себе не переносит файлы из старого writable layer. **До первого подключения нового volume к существующему развёртыванию** остановить запись, сделать согласованный backup БД и прежнего каталога, перенести содержимое проверенным способом и проверить ссылки/байты. Не перезапускать рабочие контейнеры вслепую: пустой mount может скрыть прежний каталог. Автоматического изменения существующих volumes и копирования реальных данных нет.

`FileResource.storage_path` сохраняет абсолютный путь. На прежнем Docker-размещении `/app/var/uploads` путь совместим; при переносе на другой filesystem path требуется отдельный согласованный перенос записей и содержимого. Изменения схемы БД для A-04 не нужны. Один каталог должен использоваться всеми экземплярами приложения, работающими с одной БД; локальный каталог каждого отдельного контейнера не заменяет shared persistent storage.

## Гарантии и границы транзакции

1. Upload поступает по чанкам в эксклюзивный скрытый `.uploading` файл; квота проверяется по реально прочитанным байтам.
2. После flush/fsync и проверки фактического формата содержимое атомарно переименовывается в серверное UUID-имя в том же каталоге.
3. Затем создаются запись и разрешённые связи в одной транзакции БД.
4. При обычной ошибке транзакции выполняется rollback. Содержимое удаляется только если независимый SELECT подтвердил отсутствие записи с этим storage name.
5. Если исход commit неизвестен или БД не отвечает, содержимое сохраняется, API возвращает 503 и просит проверить список. Это предпочтительнее потери успешно зафиксированного файла.
6. При удалении backend сначала сериализует DELETE по существующей строке `FileResource` условным no-op UPDATE (`updated_at=updated_at`), затем обновляет ORM-снимок, переименовывает файл в скрытый `.deleting` и удаляет запись в той же транзакции. Конкурирующий DELETE после ожидания получает `404`, если строка уже удалена, либо безопасный `503` при невозможности продолжить.
7. Ошибка commit не доказывает откат. После успешного rollback восстановление разрешено только под новой блокировкой и после независимой проверки, что та же запись всё ещё ссылается на те же storage name/path; блокировка удерживается до окончания восстановления. В зазоре rollback→повторная блокировка наличие `.deleting` запрещает другому DELETE считать отсутствующее исходное имя завершённой очисткой: возвращается `503`, запись не удаляется. Если rollback/проверка/восстановление недоступны либо ссылка уже исчезла, staged байты не возвращаются на живое имя и не уничтожаются: они остаются для офлайн-сверки, API возвращает `503`. Если commit удаления подтверждён, но окончательная физическая очистка не удалась, API сообщает `cleanup_pending=true`.

БД и filesystem не образуют общую ACID-транзакцию. Аварийное завершение между шагами может оставить orphan/staging; такие файлы скрыты и не выдаются через API без разрешённой записи. Потерянное содержимое даёт контролируемый 404, запись не уничтожается автоматически. Сверка ниже предназначена для этих случаев. Гарантия restart не равна гарантии при потере всего диска/volume; нужны backup, права доступа и мониторинг свободного места.

Проверка сложного формата выполняется вне event loop; при отмене обычного upload ожидается закрытие parser handle перед очисткой staging. Внешнее принудительное завершение процесса всё равно требует последующей сверки. Проверка формата не является антивирусом/OS sandbox. Для публичного развёртывания дополнительно настроить ограничения соединений/времени запроса, CPU/RSS, дисковую квоту и rate limiting на уровне инфраструктуры. Не увеличивать скрыто allowlist или декомпрессионные бюджеты ради приёма неподдерживаемого документа.

## Read-only аудит

Команда ниже доступна **из корня checkout той же версии приложения**, в Python-окружении с установленными зависимостями проекта. Текущий Docker image содержит `app.material_storage_audit`, но Dockerfile не копирует `scripts/check_material_storage.py`: `docker exec ... python scripts/check_material_storage.py` в штатном image не работает. Модуль аудита сам по себе не заменяет CLI с его preflight-проверками.

Перед запуском на административном хосте/в заранее согласованном административном окружении должны быть подготовлены:

- реальные `APP_ENV`, `DATABASE_URL` и `FILE_STORAGE_PATH` через утверждённую конфигурацию/секреты развёртывания, а не тестовые значения или случайный локальный `.env`;
- подключение к нужной БД из этого окружения (внутреннее Compose-имя БД не обязательно доступно с хоста); для SQLite — доступ к существующему файлу БД;
- видимость **того же** приватного volume по абсолютному пути, совпадающему с `FILE_STORAGE_PATH` и сохранёнными `FileResource.storage_path`. Для обычного аудита использовать read-only представление volume. Подстановка другого host path вместо `/app/var/uploads` не делает абсолютные ссылки совместимыми; если совпадающее представление ещё не подготовлено, запуск отложить до отдельной утверждённой настройки, не менять рабочие mounts вслепую.

После этой подготовки выполнить из корня checkout:

```bash
python scripts/check_material_storage.py
```

По умолчанию команда:

- не изменяет БД, файлы и их имена;
- не создаёт отсутствующий storage root;
- для файловой SQLite использует read-only URI и не создаёт отсутствующую БД; WAL отклоняется до подключения драйвера;
- не печатает DB URL, секреты, исходные пользовательские имена или абсолютные пути;
- возвращает JSON с IDs записей, внутренними managed-именами и безопасными категориями ошибок.

Основные поля отчёта:

| Поле | Значение |
|---|---|
| `missing_record_ids` | В БД есть ссылка на отсутствующее содержимое |
| `unsafe_record_ids` | Небезопасная/несогласованная файловая ссылка |
| `metadata_record_ids` | Допустимые записи без байтов; не ошибка хранения |
| `external_record_ids` | Записи внешних ссылок без локального файла |
| `orphaned` | Managed UUID-файлы без живой ссылки |
| `pending_uploads` | Остатки `.uploading` |
| `staged_deletions` | Остатки `.deleting` |
| `quarantined` | Уже помещённые в карантин файлы |
| `duplicate_references` | Несколько записей с одним storage name |
| `manual_attention` | Неоднозначности, не подлежащие автоматическому выбору |
| `errors` | Ошибки проверки/отказа, без приватных деталей |

Код `0` означает, что проверка завершена, **а не отсутствие найденных проблем**. Код `2` — ошибка или отказ. Проверять и содержимое JSON. На работающем приложении read-only снимок может пересечься с текущей записью/удалением; перед выводом о повреждении повторить проверку в quiescent-состоянии.

### Ограничение SQLite WAL

`mode=ro` не гарантирует отсутствие filesystem-записей для SQLite WAL: чтение может создать или изменить `-wal`/`-shm`, даже если все прежние соединения уже закрыты и остался только основной файл. Поэтому CLI сначала открывает разрешённый локальный путь БД обычным `rb`, читает заголовок и при WAL-версии чтения/записи (байты 18/19 равны `2`) **не создаёт SQL engine и не подключается к этой БД**. Это относится к обычным путям и `file:` URI, включая percent-encoded пути, как для аудита, так и для `--apply --quiescent`.

Отказ: exit `2`, JSON `{"mode":"audit","actions":[],"errors":["sqlite_wal_unsupported"]}` (при apply — `"mode":"apply"`). Это не успешная проверка и не отчёт об отсутствии проблем. Нечитаемый/неподдерживаемый путь или некорректный заголовок даёт безопасную общую ошибку `audit_unavailable`, без пути или DB URL.

WAL-источники этой командой не поддерживаются. Нужен отдельно подготовленный и проверенный согласованный источник SQLite с rollback journal либо отдельная утверждённая операторская процедура для WAL. Нельзя считать копию одного `.sqlite` при активном WAL согласованным источником: committed данные могут оставаться в WAL. CLI не делает snapshot/copy, checkpoint, переключение journal mode или `immutable=1` и не игнорирует WAL-транзакции ради продолжения проверки. Нельзя одновременно менять journal mode или подменять файл БД между preflight и подключением: проверка заголовка не блокирует другие процессы. Для строгой гарантии использовать стабильный, заранее проверенный источник без таких изменений.

## Офлайн-восстановление без уничтожения байтов

Сначала остановить **все** процессы записи: teacher/student uploads, web workers и другие запуски сверки. Сделать backup БД и каталога. После изучения read-only отчёта оператор может явно разрешить восстановление:

```bash
python scripts/check_material_storage.py --apply --quiescent --older-than-hours 24
```

`--quiescent` — утверждение оператора, не автоматическая блокировка других процессов. Без него `--apply` отклоняется. `--older-than-hours` должен быть положительным конечным числом; возраст берётся из mtime, default — 24 часа. Свежие файлы не затрагиваются.

Apply выполняет только переименования в пределах одного каталога:

- одиночный однозначный aged `.deleting` возвращается на прежнее имя, если запись ещё ссылается на отсутствующий файл;
- старые unreferenced managed файлы/staging помещаются в скрытый `.quarantine.<uuid>`, байты сохраняются;
- живые ссылки, дубликаты/неоднозначности, unmanaged имена, каталоги, symlink/junction не перемещаются;
- перед каждым действием повторно читаются ссылки БД и проверяется identity/mtime файла; результат сверяется после переименования;
- при ошибке дальнейшие действия прекращаются, уже выполненные действия остаются в `actions`; `after` содержит повторный аудит.

Не делать автоматическую permanent purge карантина. Восстановление из карантина и окончательное уничтожение требуют отдельного решения после проверки backup и ссылок. Отчёт сохраняет соответствие source/destination — хранить его с ограниченными правами вместе с эксплуатационными журналами. `manual_attention` не является разрешением выбрать произвольный кандидат.

## Проверка развёртывания

На отдельной тестовой БД и отдельном временном каталоге:

1. Загрузить настоящий поддерживаемый файл через teacher UI и сохранить ID/исходные байты.
2. Независимо проверить запись, фактический файл, teacher download и запрет чужому пользователю.
3. Проверить разрешённый student download через явную привязку, затем отзыв доступа после отвязки.
4. Полностью остановить приложение и создать новый процесс/engine с теми же БД и storage root.
5. Повторить metadata/download и побайтовое сравнение.
6. Для контейнерного окружения отдельно выполнить аналогичную проверку пересоздания контейнера с тестовым persistent volume. Проверка процесса на SQLite или `docker compose config --quiet` не является проверкой PostgreSQL/Docker runtime.

Рабочие БД, файлы и volumes не использовать для smoke-тестов. Форматы, права и API описаны в `docs/api/material-files.md`.
