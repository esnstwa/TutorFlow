# Устав проекта TutorFlow

## Проект и команда

TutorFlow — веб-платформа для совместной работы частного преподавателя и ученика. Репозиторий реализован как модульный монолит на FastAPI, SQLAlchemy/Alembic и Jinja2 с обычным JavaScript. В `docs/architecture.md` зафиксированы зоны ответственности: Артём Исаков — backend, архитектура, БД, безопасность и тестирование; Ксения Иванова — дизайн и frontend. Актуальность распределения ролей на дату защиты требует подтверждения участниками.

## Пользователи

- **Преподаватель:** ведёт собственный каталог учеников, занятия и задания, проверяет работы.
- **Ученик:** принимает приглашение преподавателя, видит назначенные ему задания и отправляет решения.

## Проблема и текущий процесс

Частному преподавателю приходится разносить расписание, список учеников, материалы, задания и ответы по календарю, мессенджерам и файлам. Ученик получает контекст и обратную связь в разных каналах. Это описание является гипотезой продукта, выведенной из реализованных функций; реальное интервью с заказчиком пока не проведено.

## Ожидаемый результат

Единый кабинет хранит связь преподавателя с учеником, занятия, домашние задания, попытки сдачи и результаты проверки. Доступ ограничен ролью и владельцем данных; состояние сохраняется в БД и восстанавливается после перезагрузки.

## Основной пользовательский сценарий

1. Преподаватель и ученик создают аккаунты и входят в систему.
2. Преподаватель создаёт карточку ученика и одноразовое приглашение.
3. Ученик принимает приглашение тем же email и получает связанный профиль.
4. Преподаватель выдаёт задание одному или нескольким своим активным ученикам.
5. Ученик отправляет комментарий и/или файл.
6. Преподаватель принимает работу либо возвращает её на доработку; повторная попытка не уничтожает историю.

## Собственная программная логика

1. **Жизненный цикл приглашения:** хранится хэш одноразового токена; учитываются срок, отзыв, изменение email и архивирование; конкурентное принятие должно иметь ровно одного победителя.
2. **Состояние работы:** `ASSIGNED → SUBMITTED → COMPLETED` или `ASSIGNED/REVISION_REQUIRED → SUBMITTED → REVISION_REQUIRED`; просрочка вычисляется из дедлайна, а не сохраняется отдельным статусом.
3. **Область доступа:** преподаватель работает только со своими учениками и заданиями, ученик — только со своим `HomeworkRecipient`; архивный ученик не получает новые назначения, но его история сохраняется.

## Модуль-кандидат для инженерного эксперимента

`students` / принятие приглашения. Эксперимент: серия из N параллельных запросов к PostgreSQL с измерением числа успешных привязок и задержки. Инвариант — ровно один успешный переход; сравниваются текущий conditional update и вариант с явной блокировкой строки. SQLite не считается достаточной средой для вывода о конкуренции.

## Внешние ресурсы и зависимости

- PostgreSQL 16 в Docker Compose; SQLite используется локально и в части тестов.
- Файловая система `var/uploads` для материалов и решений.
- HTTP-сеть и браузер; GitHub для репозитория, issue, PR и Actions.
- PyPI/npm registry при установке зависимостей и запуске CI.
- Google Calendar представлен заглушкой состояния; реальная OAuth-синхронизация не реализована.

## Ограничения

- Нет автоматической отправки приглашений, подтверждения email и восстановления пароля.
- Файлы хранятся локально; в Compose для `/app/var` нет постоянного volume.
- `/health` подтверждает процесс приложения, но не готовность БД.
- Production-развёртывание и резервное копирование не автоматизированы.
- Branch protection недоступен для текущего приватного репозитория на текущем тарифе GitHub.
- Redis, Celery, Locust и реальная интеграция Google Calendar не реализованы и не считаются текущими зависимостями.
