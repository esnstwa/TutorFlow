# Инженерный процесс TutorFlow

## Обязательный цикл

`Issue → branch → changes → checks → PR → review → merge`

1. **Issue.** Описывает проблему/ценность, границы, критерии приёмки, риски и связанные требования (`FR/NFR`). Один issue — один проверяемый результат или явно связанная группа.
2. **Branch.** Создаётся от актуального `main`; одна ветка не смешивает несвязанные изменения.
3. **Changes.** Код, миграции, тесты и документация меняются совместно. Существующие данные и обратная совместимость оцениваются явно.
4. **Checks.** Локально выполняются релевантные команды; CI обязан пройти полностью.
5. **PR.** Содержит `Closes #N`, резюме, риски, способ проверки, скриншоты для UI и migration/rollback notes для БД.
6. **Review.** Автор исправляет замечания или аргументированно разрешает их. Само-review не считается независимым.
7. **Merge.** Только после зелёного CI, независимого approval для значимого изменения и актуальности ветки. После merge ветка удаляется.

## Naming веток и коммитов

- `feature/<short-name>`, `fix/<short-name>`, `docs/<short-name>`, `chore/<short-name>`.
- Для работы Codex допустим обязательный префикс среды: `codex/<short-name>`.
- Коммиты: Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `chore:`), повелительное краткое описание; без секретов и временных файлов.

## Связь PR с issue

- В PR обязательна закрывающая ссылка `Closes #N`/`Fixes #N` для основного issue.
- Дополнительные зависимости — `Related to #N` без автоматического закрытия.
- Если требование меняется, PR ссылается на ID и обновляет `REQUIREMENTS.md`.

## Значимое изменение

Независимый review обязателен, если затронут хотя бы один объект:

- публичный API/пользовательский контракт;
- архитектура или границы модулей;
- существенное `FR/NFR`;
- схема БД/миграция/правила сохранения истории;
- build/deploy/CI/config;
- критичный дефект или защитная мера;
- аутентификация, авторизация, сессии, CSRF, файлы, секреты.

Документация ПЗ и новый CI в текущем PR считаются значимым изменением.

## Правила `main`

- `main` должна быть развёртываемой и иметь единственный Alembic head.
- Прямые push запрещены правилами команды и активным ruleset GitHub `Protect main`.
- Merge предпочтительно squash для одной логической задачи; merge commit допустим для интеграционной ветки с сохранением проверенной истории.
- Force-push и переписывание истории `main` запрещены.
- Релизный tag ставится только на commit из `main` после заполнения карточки доказательств.

## Секреты и данные

- `.env`, БД, uploads, токены, пароли, cookies, CSRF и invitation URL не коммитятся.
- В репозитории хранится только `.env.example` без реальных секретов.
- Secrets CI задаются GitHub Secrets; в логах запрещены пароль, cookie, сырой session/invitation token, CSRF, содержимое личных файлов.
- При подозрении на утечку секрет немедленно отзывается; удаление из последнего коммита не заменяет ротацию.

## Независимый review и ограничения GitHub

В репозитории есть второй collaborator `@iver-ks`, поэтому review можно запросить. Для `main` включён активный repository ruleset `Protect main`, применяемый к default branch. Он требует pull request, минимум один approval, approval последнего push, разрешение review threads и успешный status check `verify`; также запрещает удаление ветки и force-push. Legacy endpoint branch protection при этом возвращает `404`, потому что защита настроена через ruleset.

Фактически включённые правила:

- Require a pull request before merging.
- Require 1 approval; dismiss stale approvals.
- Require approval of the last push.
- Require conversation resolution.
- Require status check `verify`.
- Block force pushes and deletion of `main`.

Разрешённые способы merge: merge commit и squash merge.
