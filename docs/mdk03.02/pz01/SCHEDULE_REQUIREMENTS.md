## Уточнения приёмки по результатам Р7

Эти критерии закрепляют проверяемую часть действующего контракта расписания, не меняя общую политику авторизации. Основания — FR-07, FR-03 и NFR-02 из [общей спецификации](REQUIREMENTS.md), реализация `lesson_values`, `lesson_dict` и обработчиков расписания. Изменение правил доступа, новый формат ответа или унификация основных и совместимых маршрутов требуют отдельного согласования.

| Сценарий | Проверяемый исход |
|---|---|
| K1. Создание через `POST /api/lessons` | В сохранённой записи предмет обязателен. В теле запроса `subject` можно опустить, тогда используется предмет выбранного ученика. Явно переданный предмет должен быть непустой строкой после удаления пробелов по краям. Пустая строка, только пробелы и `null` отклоняются с HTTP 422. При пропуске статуса сохраняется `scheduled`. Если ни место, ни ссылка не переданы, в сохранённой записи и ответе `lesson.location = ""` и `lesson.meeting_url = null`. При повторном чтении сверяются также предмет и статус. |
| K2. Равный и обратный интервал при создании | HTTP 422 на `POST /api/lessons`, JSON с непустым строковым `detail`, объясняющим, что окончание должно быть позже начала. Полный снимок `lessons` неизменен. Текст сообщения читаем для человека, машинный код ошибки не вводится. |
| K3. Чужая активная или своя архивная карточка при создании | HTTP 422 и одинаковый внешний JSON-ответ `{"detail":"Ученик не найден"}` для обоих случаев. Ответ не сообщает принадлежность или состояние чужой карточки. Полный снимок `lessons` неизменен. |
| K4a. Повторное чтение | Отдельный запрос детали и новая ORM-сессия проверяют сохранённую запись. Сверяются ID, ученик, предмет, тема, начало, конец и статус. Эта проверка подтверждает новое чтение в текущем процессе. |
| K4b. Перезапуск приложения | Первый процесс должен завершиться. Второй запускается на той же постоянной БД. После нового входа без прежней cookie сверяются запись и календарь. Лог с двумя процессами и новым входом хранится отдельно от прогона K4a. Перезапуск СУБД в этот критерий не входит. |
| K5. Корректная и некорректная защита | В основной тройке запросов используются одинаковые данные и допустимый источник: `Origin` соответствует схеме, хосту и эффективному порту приложения, `Sec-Fetch-Site: same-origin`. Действующий сессионный токен при валидной правке даёт 200. Могут измениться целевые бизнес-поля и служебный `updated_at` только этой записи. Отсутствующий или неверный токен даёт 403, все строки и столбцы остаются прежними. |

В остальных изменяющих запросах расписания переданный `Origin` обязан соответствовать origin приложения. Переданный `Sec-Fetch-Site` допускает значения `same-origin` и `none`. Отсутствие одного или обоих заголовков само по себе не причина отказа. При этом действующая сессия, корректный CSRF-токен, роль, владение и предметные проверки по-прежнему обязательны. Это проверяемая граница действующего NFR-02 для расписания, а не правило для регистрации и входа.

Формат `detail` в K2/K3 относится к основному маршруту создания. Совместимые маршруты сохраняют действующий JSON с `ok: false` и `error` для ошибок обработки содержимого. Для ошибок защиты применяются действующие ответы общей зависимости авторизации.

Для учебного минимума расписания достаточно создания разового занятия и повторного просмотра. Перенос, правка и отмена существуют и проверяются по применимым ограничениям доступа. Уточнение не утверждает новые правила пересечений, касания границ, переходов статусов и конкурентной записи. Владелец подтвердил политику временных конфликтов для отдельного изменения. См. [проект CR-001](CR001_SCHEDULE_CONFLICTS.md). Повторяющиеся занятия не входят в подтверждённый объём.
