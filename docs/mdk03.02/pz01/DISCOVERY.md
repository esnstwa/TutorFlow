## Текущий процесс

Преподаватель регистрируется, входит, создаёт карточку ученика, формирует одноразовую ссылку и передаёт её вручную. Ученик регистрируется/входит с целевым email и принимает приглашение. После привязки преподаватель ведёт расписание и выдаёт задания; ученик сдаёт работу; преподаватель принимает её либо возвращает на доработку.

До этого изменения обязательного CI, issue/PR-шаблонов и формального Quality Gate в репозитории не было. В истории есть три слитых PR без зафиксированного review decision и несколько прямых merge/feature-коммитов.

## Подтверждённые потребности

- раздельный доступ преподавателя и ученика;
- явная связь карточки ученика с аккаунтом через приглашение;
- сохранение занятий, заданий, файлов, попыток и проверок;
- несколько получателей одного задания без копирования `Homework`;
- сохранение истории повторных отправок;
- защита изменяющих запросов сессией и CSRF;
- архивирование карточки без уничтожения истории.

## Примеры ситуаций из реализованного поведения

- При повторном или просроченном приглашении backend отклоняет привязку.
- При попытке преподавателя назначить задание чужому/архивному ученику запрос отклоняется.
- При возврате работы новая отправка создаёт новый `HomeworkSubmission`.
- Если дедлайн прошёл при статусе `ASSIGNED`, UI показывает «Просрочено», не изменяя сохранённый статус.
- Неавторизованный API получает `401`, пользователь не той роли — `403`, чужой объект обычно скрывается как `404`.

## Ограничения обследования

- Нет записей интервью, продуктовой аналитики и наблюдения за реальными пользователями.
- Нет production-окружения и измерений нагрузки.
- Не подтверждены политика хранения файлов, сроки хранения персональных данных и допустимые браузеры.
- Реальное оппонирование другой командой не проводилось.

## Предположения команды (требуют подтверждения)

- Главная ценность — единая цепочка «связать ученика → выдать → сдать → проверить».
- Для Baseline MVP достаточно текстовых заданий; файлы и календарь повышают ценность, но не нужны для минимальной цепочки.
- Один аккаунт ученика пока связывается только с одной карточкой `Student`.
- Ручная передача ссылки допустима на первом этапе.

## Принятые решения ПЗ №1

- Не расширять продукт на оценки, группы, recovery, email-доставку и фоновые задачи без подтверждения.
- Baseline MVP строить вокруг сквозного задания и ролевой изоляции.
- Создать проверяемые FR/NFR с фактическим статусом.
- Ввести CI и шаблоны процесса, не объявляя CI/review успешными до реального выполнения.
- Интервью и оппонирование оставить явными внешними TODO.
