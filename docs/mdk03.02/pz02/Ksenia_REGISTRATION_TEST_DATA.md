домашних заданий в этот документ не входят.

> фактический код текущего checkout. Скрытые критерии преподавателя не
> предполагаются.

### Граница имени длиной 31

Технически текущая схема `RegisterRequest` отклоняет 31 символ из-за
`Field(max_length=30)` и регулярного выражения. Frontend при вводе вызывает
`filterNameInput()` и обрезает значение до 30 символов (`register.js:77–90`).

Это не является независимым доказательством правильности UX. Возможны два
контракта:

1. отклонять исходное значение и показать ошибку;
2. автоматически обрезать ввод до 30 символов.

До решения владельца требований значение `31` хранится как диагностический
набор, но не получает автоматизированного утверждения «должно пройти» или
«должно быть отклонено» на уровне пользовательского сценария.

### Граница email 253/254/255

Выполненная проверка текущей `RegisterRequest` дала:

- 253 символа — схема принимает;
- 254 символа — схема принимает;
- 255 символов — `EmailStr` отклоняет как слишком длинный адрес.

Это подтверждает технический контракт используемого валидатора, но в FR/NFR
ПЗ №1 отдельный лимит email не сформулирован. Поэтому в тестах допустимо
проверить контракт схемы, но нельзя выдавать его за явно согласованное
продуктовое требование без уточнения.

## 4. Воспроизводимое исходное состояние

### Базовая pytest-инфраструктура

Переиспользуются существующие объекты из `tests/conftest.py`:

- `TEST_ENGINE` — SQLite in-memory с `StaticPool`;
- `TestingSessionLocal` — сессии тестовой БД;
- `override_get_db()` — dependency override для приложения;
- `database_schema` — создание схемы, development seed и удаление схемы после
  завершения pytest-сессии.

В текущем `database_schema` seed выполняется один раз на pytest-сессию и не
является независимым состоянием каждого теста. Поэтому будущие тесты Ксении
должны:

1. не использовать seeded identities как авторизованных пользователей;
2. создавать пользователей только через регистрацию или через локальную
   фабрику данных теста;
3. использовать namespace `kseniya.*@example.com`;
4. не полагаться на числовые ID;
5. очищать созданные `User` и связанные `AuthSession` после сценария либо
   использовать отдельную транзакционную изоляцию в следующем этапе;
6. не направлять запросы в `.env`/production PostgreSQL.

### Подготовка

Из корня репозитория:

```text
.venv/Scripts/python.exe -m pytest -p no:cacheprovider tests/test_auth_integration.py -q
```

Команда использует существующий `tests/conftest.py`, создаёт in-memory SQLite,
поднимает схему и seed автоматически. Файл данных импортируется обычным
Python-импортом; он не меняет БД и не требует дополнительных библиотек.

### Сброс

- При завершении pytest-сессии `database_schema` выполняет `drop_all()`.
- Для отдельного запуска не использовать постоянный DB URL из `.env`.
- При будущей реализации тестов удалять только сущности с namespace
  `kseniya.*@example.com` и их `AuthSession`; seed-пользователей `anna@tutorflow.local`
  и `student@tutorflow.local` не трогать.
- `tests/data/registration_kseniya.py` не содержит состояния и очищать его не
  нужно.

## 5. Техники и зафиксированный результат этапа 2

Используются три техники:

1. **Классы эквивалентности** — роли, форматы email, состав пароля, типы
   ошибок и confirmation.
2. **Граничные значения** — имя 1/2/30/31, пароль 7/8/128/129, email
   253/254/255.
3. **Переходы состояний** — `ROLE → NAME → EMAIL → PASSWORD → SUBMITTING →
   COMPLETE`, включая возвраты на шаг с ошибкой `409/422`.

Короткий чек-лист:

- [ ] teacher/student дают разные ролевые redirect.
- [ ] Отсутствующая и неизвестная роль отклоняются.
- [ ] Проверены границы имени и дефис.
- [ ] Проверены формат, нормализация и duplicate email.
- [ ] Проверены границы и состав пароля.
- [ ] Проверено совпадение confirmation.
- [ ] Успешная регистрация сохраняет пользователя и создаёт сессию.
- [ ] Login, logout, CSRF и role access используют изолированную сессию.
- [ ] Пароль и raw session token не сохраняются открыто.
- [ ] UI-граница 360 px отмечена как отдельная browser-проверка, а не как
      доказанная backend-тестами.

## 6. Изолированные зависимости и ограничения

Изолируются или подменяются существующей инфраструктурой:

- тестовая SQLite-БД вместо production/PostgreSQL;
- `get_db` через существующий dependency override;
- cookie jar каждого `TestClient`;
- `sessionStorage`, `localStorage`, DOM и `fetch` в JS-тестах;
- synthetic email/password/role values.

Не подтверждаются этим этапом:

- реальный PostgreSQL после `alembic upgrade head`;
- запуск приложения за HTTPS reverse proxy;
- реальный Chromium, keyboard flow и viewport 360 px;
- конкурентная регистрация одного email;
- email delivery, recovery и email verification;
- rate limiting login;
- корректность продукта относительно невыданных преподавателем требований.
