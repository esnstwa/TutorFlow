# Реестр рисков — расписание Артёма (ПЗ №2)

**Область:** FR-07 и связанные FR-03, FR-16, NFR-02. **Источники:** [Requirements 1.0](../pz01/REQUIREMENTS.md), [TEST_CASES_ARTEM.md](TEST_CASES_ARTEM.md), [COVERAGE_ARTEM.md](COVERAGE_ARTEM.md), [MUTATION_ARTEM.md](MUTATION_ARTEM.md), `app/services.py`, `app/web/router.py`, `app/models.py` и фактические результаты наборов.

**Границы доказательства:** ранее задокументировано 31 PASS из 31 собранной проверки; мутационный опыт A-SCH-04 дал поведенческий FAIL, после восстановления — 31 PASS. Финальный повторный аудит и результаты его запусков приведены ниже. Фикстура использует отдельную in-memory SQLite на каждый тест, подменяет `get_db` и `get_current_teacher`, поэтому не проверяет реальный вход/сессию/CSRF расписания. PostgreSQL CI проверяет миграции, не расписательные сценарии. GitHub Actions для локальных изменений не запускался.

## Матрица и правила оценки

Вероятность и ущерб — **качественные экспертные оценки**, не статистика частоты дефектов. Приоритеты присвоены по матрице методички:

| Вероятность \ Ущерб | Небольшой | Значимый | Тяжёлый |
|---|---|---|---|
| Низкая | Низкий | Средний | Высокий |
| Средняя | Средний | Высокий | Высокий |
| Высокая | Средний | Высокий | Высокий |

- **Низкая вероятность:** путь явно защищён несколькими проверками/ограничениями; нужна нетипичная регрессия.
- **Средняя:** правдоподобно при обычном изменении интеграции или требований; защита неполная.
- **Высокая:** дефект легко воспроизводится обычным сценарием или уже присутствует относительно согласованного ожидаемого поведения.
- **Небольшой ущерб:** локальная обратимая помеха без ошибочной сохранённой записи; **значимый:** неверное расписание или состояние требует ручного исправления; **тяжёлый:** нарушение изоляции пользователей, повторное бронирование либо массовая/труднообратимая порча данных.

## Риски

### R-SCH-01 — занятие привязано к чужому или неактивному ученику
- **Событие → последствие:** запрос использует чужой или архивный `student_id`; занятие создаётся вне области преподавателя или для недоступной карточки. Возможны раскрытие данных другого преподавателя и порча истории.
- **Требование / функция:** FR-07; `create_entity(..., "lesson", ...)` и `scoped_student` (`app/services.py:181,294–304`); архив проверяется отдельно.
- **Вероятность:** средняя — ownership-фильтр и архивная проверка есть, но их регрессия правдоподобна.
- **Ущерб:** тяжёлый — пересекает границу данных преподавателей.
- **Приоритет:** **высокий**.
- **Связанные кейсы / статус:** A-SCH-04 и A-SCH-05 — **PASS** в последнем наборе. Мутация удаления `Student.teacher_id == teacher_id` дала A-SCH-04 **FAIL** (`HTTP 200`, запись сохранена) и после восстановления **PASS**. Это конкретное свидетельство чувствительности к регрессии ownership, не доказательство реальной авторизации.
- **Режим:** каждый PR — полный pytest и фокусный набор; повторно при изменении student-scope, создания урока или авторизации.
- **Остаточный риск / решение:** остаётся разрыв между предметной проверкой ID ученика и проверкой реальной сессии. Для авторизационной границы см. R-SCH-08 и предложение A-SCH-21.

### R-SCH-02 — некорректный временной интервал сохранён
- **Событие → последствие:** `end_at <= start_at` проходит API/сервис; появляется нулевое или обратное занятие, ломая календарь и занятость слотов.
- **Требование / функция:** FR-07 прямо требует отклонять `end_at <= start_at`; сервис `app/services.py:305–308`, DB constraint `ck_lessons_time_order` (`app/models.py:79–84`).
- **Вероятность:** низкая — есть проверка в сервисе, DB CHECK и граничные тесты.
- **Ущерб:** значимый — неверное расписание, хотя текущий CHECK служит дополнительным барьером.
- **Приоритет:** **средний**.
- **Связанные кейсы / статус:** A-SCH-02/A-SCH-03 (`end == start`, `end < start`) — **PASS**, отказ и отсутствие новой записи.
- **Режим:** каждый PR; дополнительно при изменениях datetime/localization, сервиса, схемы или миграции.
- **Остаточный риск / решение:** покрыты равный и обратный интервалы; не доказаны все production-диалекты БД и реальные интеграционные преобразования даты/времени. Для обычной регрессии текущего контракта новых unit-кейсов не требуется.

### R-SCH-03 — двойное бронирование одного преподавателя
- **Событие → последствие:** пересекающиеся занятия сохраняются для одного преподавателя; расписание обещает один временной слот нескольким ученикам.
- **Требование / функция:** FR-07 не устанавливает политику конфликтов; отдельное предложение [FR07_OVERLAP_CHANGE_PROPOSAL.md](../pz01/FR07_OVERLAP_CHANGE_PROPOSAL.md) ожидает решения владельца/review. A-SCH-08/11 проверяют два неотменённых занятия при создании/переносе. Реализация проверки — `app/services.py:309–311`, перенос — `app/web/router.py:239–241`.
- **Вероятность:** средняя — обычные последовательные запросы проверяются, но проверка «прочитать конфликт → вставить» может гоняться при параллельных запросах; отдельного DB exclusion/unique constraint в `Lesson` нет.
- **Ущерб:** тяжёлый — преподавателю назначаются несовместимые занятия, требуется ручное согласование.
- **Приоритет:** **высокий**.
- **Связанные кейсы / статус:** A-SCH-08 — **PASS как проверка текущей реализации** (частичное/вложенное пересечение при создании); A-SCH-11 — **PASS как проверка текущей реализации** (пересечение при переносе с сохранением исходного слота). Эти две пары соответствуют предложенному правилу, если оно будет утверждено; до решения владельца это не принятое требование. SQL сейчас также блокирует `cancelled`; предложение не решает этот случай (A-SCH-09). Проверки последовательные, конкурентную гарантию не доказывают.
- **Режим:** имеющиеся случаи — каждый PR и при изменении conflict logic; конкурентный сценарий — отдельный PostgreSQL integration run периодически и при изменении сервиса/изоляции транзакций.
- **Остаточный риск / решение:** существенный — гонка не закрыта существующими доказательствами. После approval требования предложен A-SCH-22: два синхронизированных POST одного слота в PostgreSQL, затем проверка, что принят максимум один запрос и в БД только одно занятие, если владелец подтвердит конкурентную гарантию как часть правила.

### R-SCH-04 — перенос не сохраняет длительность или портит исходное занятие при отказе
- **Событие → последствие:** перенос теряет исходную длительность/данные или частично меняет слот после невалидного запроса/конфликта.
- **Требование / функция:** FR-07, FR-16; `reschedule` вычисляет прежнюю длительность, проверяет конфликт до присваивания и откатывает `ValueError` (`app/web/router.py:229–249`).
- **Вероятность:** низкая — ветки успешного переноса, конфликтов и отсутствующего времени проверяются.
- **Ущерб:** значимый — неправильное время занятий и ручное восстановление.
- **Приоритет:** **средний**.
- **Связанные кейсы / статус:** A-SCH-10 — **PASS** (успех и сохранение 60 минут); A-SCH-11 — **PASS как проверка текущего поведения** (отказ при пересечении, исходное время сохранено), но нормативное основание pending по R-SCH-03; A-SCH-16 — **PASS** (нет `start`, дата и время не меняются).
- **Режим:** каждый PR и при изменении маршрута переноса, datetime-кода или транзакций.
- **Остаточный риск / решение:** ошибки именно на commit/DB-разрыве при переносе не покрыты текущими SQLite-кейсами; при существенном изменении persistence добавить сценарий к PostgreSQL integration, не меняя контракт без необходимости.

### R-SCH-05 — ошибка запроса оставляет частичную запись или несогласованное состояние
- **Событие → последствие:** ошибка валидации/ограничения после начала операции оставляет занятие или часть изменений в БД.
- **Требование / функция:** FR-16 и обработчики rollback в `app/web/router.py`; `Lesson` имеет ограничения на status и время (`app/models.py:79–84`).
- **Вероятность:** низкая — для обычных отказов тесты сравнивают состояние до/после; commit guard закрывает проверенный integrity-error путь.
- **Ущерб:** тяжёлый — неконсистентные записи расписания, повторные обращения и ручное исправление.
- **Приоритет:** **высокий**.
- **Связанные кейсы / статус:** A-SCH-02/03, A-SCH-04/05, A-SCH-08, A-SCH-11, A-SCH-13…16, A-SCH-18 — **PASS** по отказам/неизменности состояния; A-SCH-19 — **PASS**: искусственный DB CHECK failure в отдельной SQLite приводит к 422 и нулю сохранённых записей.
- **Режим:** каждый PR; PostgreSQL transaction/error path — при изменении модели, миграций, DB-обработки и перед выпуском.
- **Остаточный риск / решение:** A-SCH-19 подтверждает конкретный SQLite CHECK/rollback, но не PostgreSQL и не сбой соединения/commit при переносе. В CI PostgreSQL запускаются миграционные проверки, не расписательный rollback-тест. Предложен A-SCH-23 — повторить проверку атомарности на одноразовой PostgreSQL test DB; не выполнять на пользовательской БД.

### R-SCH-06 — недопустимый переход статуса занятия
- **Событие → последствие:** разрешённый ярлык статуса устанавливается из неподходящего исходного состояния; например, изменение `cancelled` на `completed_paid` может исказить историю/отчётность, если переход запрещён продуктом.
- **Требование / функция:** FR-07 перечисляет четыре допустимых статуса, но не задаёт граф переходов; `update_compatible_lesson` проверяет принадлежность набору, а не исходный статус (`app/web/router.py:260–276`).
- **Вероятность:** средняя — API сейчас принимает любой из четырёх статусов из любого состояния; дефект зависит от ещё не утверждённой политики.
- **Ущерб:** значимый — ошибочная история и возможное влияние на пользовательский учёт занятий.
- **Приоритет:** **высокий**.
- **Связанные кейсы / статус:** A-SCH-07 — **PASS** для принятия четырёх значений и отказа неизвестному. Он **не проверяет переходы** между разрешёнными статусами.
- **Режим:** ручное согласование владельцем требования сейчас; после утверждения — каждый PR при изменении модели/status endpoint.
- **Остаточный риск / решение:** нельзя объявить текущую свободу переходов правильной или неправильной. Сначала определить допустимые переходы (включая повторное открытие/отмену); затем при необходимости добавить A-SCH-24 с таблицей исходное состояние × действие.

### R-SCH-07 — неодинаковая политика слота для отмены и касания границ
- **Событие → последствие:** отменённый урок продолжает блокировать время либо касающийся интервал трактуется не так, как ожидает пользователь; результат — потерянная доступность или двойное бронирование.
- **Требование / функция:** FR-07 не задаёт эти два правила. Код считает collision по всем статусам и использует строгое пересечение (`existing.start < new.end` и `existing.end > new.start`), поэтому `cancelled` сейчас блокирует слот, точное касание не конфликтует (`app/services.py:309–311`; аналогично перенос в `app/web/router.py:239–241`).
- **Вероятность:** средняя — поведение реализации определено, но ожидаемое продуктовое поведение не согласовано.
- **Ущерб:** значимый — ошибочный отказ или бронирование, требующее ручного вмешательства.
- **Приоритет:** **высокий**.
- **Связанные кейсы / статус:** A-SCH-09 (конфликт с `cancelled`) и A-SCH-12 (касание) — **не автоматизированы / ожидают уточнения**; не считать PASS или FAIL. A-SCH-08/A-SCH-11 покрывают только строгое активное пересечение в текущей реализации; подтверждённым продуктовым правилом это не считать.
- **Режим:** вручную до решения; после внесения правила в FR-07 — каждый PR.
- **Остаточный риск / решение:** открыт вопрос владельцу: отмена освобождает слот? касание интервалов разрешено как `[start, end)`? Не менять ожидания тестов до ответа.

### R-SCH-08 — расписательный тест не подтверждает реальную авторизацию и среду БД
- **Событие → последствие:** регрессия cookie/session/CSRF/role или несовместимость с PostgreSQL остаётся незамеченной набором, хотя 31 SQLite-проверка проходит.
- **Требование / функция:** FR-03, FR-07, NFR-02; реальные `get_current_teacher` проверяют сессию/роль и для изменяющих методов CSRF (`app/core/auth.py:18–33`). Но в `schedule_case` оба `get_db` и `get_current_teacher` подменены (`tests/test_schedule_pz02.py:58–70`).
- **Вероятность:** средняя — auth-код и отдельные auth-тесты существуют, но расписательный набор не проходит через них; модель SQLite отличается от PostgreSQL.
- **Ущерб:** тяжёлый — возможен доступ/изменение расписания не тем пользователем либо незамеченный дефект диалекта/транзакций.
- **Приоритет:** **высокий**.
- **Связанные кейсы / статус:** прямых A-SCH-кейсов с реальной cookie/CSRF нет. Все 31 кейс — **PASS в тестовой среде с dependency override**, не доказательство настоящего login-flow. Существующие auth-тесты проверяют сессии/роль отдельно, но не являются проверкой API расписания.
- **Режим:** обычные тесты — каждый PR; integration с реальными auth dependencies — при изменении auth/router/session и периодически/перед релизом на disposable DB.
- **Остаточный риск / решение:** высокий до интеграционной проверки. Предложен A-SCH-21: через настоящий login получить teacher cookie+CSRF, вызвать создание своего урока и запрос чужого ученика; проверить отказ и неизменность БД; отдельно вызвать teacher endpoint ученическим аккаунтом и ожидать 403. Не подменять `get_current_teacher`.

## Риск-ориентированная достаточность и режим проверок

### Каждый PR / изменение

- Полный `pytest -q` включает индивидуальный файл расписания; отдельный coverage-шаг запускает именно `tests/test_schedule_pz02.py`. Отчёт покрытия отмечает 100% строк и conditional branch arcs в выделенных диапазонах, но эти цифры не доказывают корректность внешней БД, конкурентность или реальную авторизацию.
- Фокусный набор действительно снижает риски invalid interval, обычного foreign/archived student, последовательного пересечения, основных путей переноса и ряда отказов/rollback. Мутационный результат отдельно подтверждает чувствительность A-SCH-04 к удалению teacher-scope фильтра.
- Конфигурация workflow описана, но GitHub Actions для текущих локальных изменений здесь не запускался; прошлые локальные PASS не называть CI run.

Команды для воспроизведения наборов из корня репозитория:

```text
./.venv/Scripts/python.exe -m pytest tests/test_schedule_pz02.py -q
./.venv/Scripts/python.exe -m pytest -q
node --test tests/auth-wizard.test.cjs tests/student-lifecycle.test.cjs
node tests/test_session_fetch.cjs
```

Покрытие воспроизводится командой из [COVERAGE_ARTEM.md](COVERAGE_ARTEM.md); условия мутационного эксперимента и точный patch — в [MUTATION_ARTEM.md](MUTATION_ARTEM.md). Локальный общий `TEST_PLAN.md` прочитан только для контекста, не отслеживается Git и не является источником утверждённого правила. Самостоятельное [предложение по FR-07](../pz01/FR07_OVERLAP_CHANGE_PROPOSAL.md) также имеет статус PENDING. Данные в `pyproject.toml` и `COVERAGE_ARTEM.md` отражают фактическое состояние pytest-cov.

### Проверка высоких рисков

- **R-SCH-01:** A-SCH-04/05 подтверждают отказ для чужого/архивного ученика; мутация A-SCH-04 показывает чувствительность к снятию teacher-scope. Это снижает риск регрессии фильтра, но не риск обхода реальной сессии.
- **R-SCH-03:** A-SCH-08/A-SCH-11 соответствуют примерам из отдельного предложения, но правило ещё не утверждено; сценарии последовательные и не проверяют отмену, границу касания или конкурентную гонку. A-SCH-22 потребуется, если владелец включит конкуренцию в критерий.
- **R-SCH-05:** A-SCH-19 подтверждает rollback при конкретном SQLite CHECK error, но не PostgreSQL/commit failure; остаточный риск сохраняется до A-SCH-23.
- **R-SCH-06:** A-SCH-07 проверяет значения статуса, но не переходы. Риск не снижен, пока владелец требования не утвердит граф и не появится A-SCH-24.
- **R-SCH-07:** A-SCH-09/12 не реализованы и не имеют статуса PASS/FAIL; существующие тесты не снижают риск расхождения продуктовой политики.
- **R-SCH-08:** прямой расписательной проверки реальной cookie/CSRF/role нет; нужен A-SCH-21. Отдельные auth-тесты не заменяют интеграцию с расписательным маршрутом.

Финальная проверка аудита 2026-10-12: индивидуальный pytest — 31 PASS (1 Starlette deprecation warning); полный pytest — 217 PASS (1 warning); JavaScript — 34 PASS; session-fetch — 6 PASS. Локальные TOML/YAML и структурные проверки workflow прошли, `pip check` и `pip install --dry-run -e '.[dev]'` успешны. Мажоры Actions проверены по официальным release/metadata (Node 24); `actionlint` отсутствует. Удалённый GitHub Actions run не запускался.

### Для реальной интеграционной среды

1. A-SCH-21 — реальный session/role/CSRF на `/api/lessons` без auth override (FR-03/FR-07/NFR-02).
2. A-SCH-22 — два синхронизированных пересекающихся запроса на PostgreSQL, **если после approval владелец подтвердит, что правило включает конкурентные запросы**.
3. A-SCH-23 — атомарность ошибки commit/rollback для расписательного изменения на отдельной PostgreSQL test DB (FR-16). Текущий CI PostgreSQL step проверяет Alembic, не эту логику.

Это предложения; они не реализованы и не запускались. Дополнительные тесты в рамках текущего пересмотра не добавлялись.
