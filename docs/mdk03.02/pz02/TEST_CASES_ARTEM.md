# Тест-кейсы — расписание (Артём)

**Требование:** FR-07 (`docs/mdk03.02/pz01/REQUIREMENTS.md:27`); для сохранения — FR-16 (`:36`).
**Риск-ориентированный пересмотр:** [RISK_REGISTER_ARTEM.md](RISK_REGISTER_ARTEM.md).
**Граница:** сервис создания `app/services.py:294–321`; API `app/web/router.py:229–249,252–292,372–381`; проверка сохранённого состояния — новая DB session. `POST /api/mock/lessons/{id}/reschedule` — историческое имя маршрута; он использует SQLAlchemy DB, а не in-memory mock.

**Предусловие каждого кейса:** отдельное чистое тестовое состояние, преподаватель T, активный ученик S (при необходимости T2/S2); дата без seed-занятий. `schedule_case` создаёт отдельный in-memory SQLite engine на каждый тест (`StaticPool`, внешние ключи включены), синтетические записи и TestClient; `get_db` направлен на эту БД, а тестовая dependency выдаёт преподавателя T. Teardown удаляет таблицы и engine. Production service/router/model исполняются реально, без mock бизнес-логики. Часы и внешние сервисы не нужны.

**Интерпретация ожиданий:** если FR требует отказ, но не задаёт HTTP-код/тело, зафиксированный код API — дополнительная проверка текущего API-контракта, не требование FR. Для A-SCH-08/11 само правило запрета пересечения пока предварительное и нуждается в подтверждении; PASS означает соответствие текущей реализации, не приёмку продуктового требования.

## Кейсы

### A-SCH-01 — создать занятие в свободном интервале
- **Техника / требование:** классы эквивалентности, валидные данные / FR-07, FR-16.
- **Начальное состояние и вход:** у T есть активный S; `student_id=S.id`, `date=2026-11-10`, `start=10:00`, `end=11:00`, `topic=Алгебра`, допустимый статус `scheduled`.
- **Действия:** `POST /api/lessons`; прочитать запись в новой DB session, запросить её через `GET /api/lessons/{id}`, затем проверить календарный список как с date-фильтром, так и без него.
- **Ожидание:** успех; запись принадлежит T и S, интервал 10:00–11:00, тема и статус сохранены; detail и calendar API возвращают то же занятие. Основание: FR-07 требует создание и отображение после reload; FR-16 — доступность после новой сессии.

### A-SCH-02 — нулевая длительность
- **Техника / требование:** граничное значение `end_at == start_at` / FR-07.
- **Состояние и вход:** чистое состояние; `start=10:00`, `end=10:00`.
- **Действия:** создать занятие.
- **Ожидание:** HTTP 422, запись отсутствует. Прямой критерий FR-07: `end_at <= start_at` отклоняется.

### A-SCH-03 — окончание раньше начала
- **Техника / требование:** класс невалидного интервала / FR-07.
- **Состояние и вход:** `start=11:00`, `end=10:00` в одной дате.
- **Действия:** создать занятие.
- **Ожидание:** HTTP 422, запись отсутствует; FR-07 требует отклонять интервал с `end_at <= start_at`.

### A-SCH-04 — чужой ученик
- **Техника / требование:** класс эквивалентности «не собственный объект» / FR-07.
- **Состояние и вход:** S2 принадлежит T2; автор запроса T; иначе валидный свободный интервал.
- **Действия:** создать занятие с `student_id=S2.id`.
- **Ожидание:** запрос отклонён и занятие не создано; текущая реализация возвращает 422 `Ученик не найден`. FR-07 требует собственного ученика, но не задаёт HTTP-код/ошибку; тест фиксирует отказ (4xx), не конкретный код.

### A-SCH-05 — архивный ученик
- **Техника / требование:** класс невалидного состояния объекта / FR-07.
- **Состояние и вход:** S принадлежит T, но `archived_at` задан; интервал валиден.
- **Действия:** создать занятие для S.
- **Ожидание:** запрос отклонён и запись не создана; текущая реализация возвращает 422 `Ученик не найден`. FR-07 говорит об активном ученике, но не задаёт HTTP-код; тест проверяет отказ (4xx), не конкретный код.

### A-SCH-06 — граница длины заметки
- **Техника / требование:** граничные значения 500/501 / FR-07.
- **Состояние и вход:** существующее занятие; для каждого запроса отправить `status=scheduled`, `topic=Алгебра`, `location=Кабинет`, `materials=[]`, `teacher_note` длиной сначала 500, затем 501 символ.
- **Действия:** выполнить PATCH `/api/lessons/{id}` независимо на чистой/восстановленной записи; после каждого прочитать занятие новой DB session.
- **Ожидание:** 500 символов сохраняются; 501 отклоняется и прежняя заметка остаётся. FR-07 задаёт максимум 500 символов. Восстановить исходное состояние между запросами.

### A-SCH-07 — классы допустимого и неизвестного статуса
- **Техника / требование:** классы статусов / FR-07.
- **Состояние и вход:** существующее занятие; отдельно проверить каждый `scheduled`, `completed_unpaid`, `completed_paid`, `cancelled`, а затем неизвестный `cancelled_by_student`. PATCH `/api/lessons/{id}` передаёт `topic=Алгебра`, `location=Кабинет`, `materials=[]`, `teacher_note=""` и очередной статус.
- **Действия:** для каждого значения независимо PATCH; прочитать запись новой DB session; сбросить состояние между вариантами.
- **Ожидание:** четыре разрешённых статуса сохраняются; неизвестный отклоняется (422), прежний статус остаётся. FR-07 перечисляет четыре допустимых статуса и требует отклонять неизвестный. Правила перехода между допустимыми статусами не определены и этим кейсом не проверяются.

### A-SCH-08 — пересечение при создании
- **Техника / источник:** граничные классы «строго пересекается / не пересекается». FR-07 не задаёт политику конфликтов; это предварительное ожидаемое поведение, описанное в [предложении по FR-07](../pz01/FR07_OVERLAP_CHANGE_PROPOSAL.md). Решение владельца и review ещё не получены.
- **Состояние и вход:** занятое занятие T 10:00–11:00; создать для другого ученика 10:30–11:30.
- **Действия:** POST создания.
- **Ожидание (предложение, PENDING):** если правило из [предложения по FR-07](../pz01/FR07_OVERLAP_CHANGE_PROPOSAL.md) будет утверждено, запрос отклоняется, исходная запись неизменна. Тест сейчас фиксирует это поведение (в реализации — 422), но PASS подтверждает только текущую реализацию; решение по требованию не оформлено.

### A-SCH-09 — слот после отмены
- **Техника / требование:** таблица решений `status × collision`; кандидат к FR-07, **УТОЧНИТЬ**.
- **Состояние и вход:** занятие T 10:00–11:00 со статусом `cancelled`; создать другое 10:30–11:30.
- **Действия:** POST создания.
- **Ожидание:** не определено FR-07. Рекомендация: отменённое занятие не блокирует слот; если принято — создание успешно. До подтверждения результат считать открытым вопросом, не тестовым oracle.

### A-SCH-10 — перенос сохраняет длительность
- **Техника / требование:** классы эквивалентности — свободный целевой слот / FR-07, FR-16.
- **Состояние и вход:** существующее занятие длительностью 60 минут; целевой интервал свободен; дата `2026-11-12`, начало `13:00`.
- **Действия:** POST `/api/mock/lessons/{id}/reschedule`; затем запросить занятие/прочитать новую DB session.
- **Ожидание:** успешный перенос; начало 13:00, конец 14:00, идентификатор и длительность прежние. Тест нужен как отдельная проверка целевого API; существующий похожий сценарий — `tests/test_teacher_cabinet.py:88–97`.

### A-SCH-11 — перенос в пересекающийся интервал
- **Техника / источник:** граничные классы «строго пересекается / не пересекается». FR-07 не задаёт политику конфликтов; это предварительное ожидаемое поведение, описанное в [предложении по FR-07](../pz01/FR07_OVERLAP_CHANGE_PROPOSAL.md). Решение владельца и review ещё не получены.
- **Состояние и вход:** переносимое занятие 60 минут; другое занятие 10:00–11:00; перенос целится в 10:30.
- **Действия:** reschedule; после ответа проверить старые даты/время.
- **Ожидание (предложение, PENDING):** если правило из [предложения по FR-07](../pz01/FR07_OVERLAP_CHANGE_PROPOSAL.md) будет утверждено, перенос отклоняется, исходный слот сохраняется. Тест сейчас фиксирует это поведение (в реализации — 422), но PASS подтверждает только текущую реализацию; решение по требованию не оформлено.

### A-SCH-12 — касание границ соседних занятий
- **Техника / требование:** граничное значение `end == next.start`; **УТОЧНИТЬ**.
- **Состояние и вход:** занятие 10:00–11:00; новое занятие 11:00–12:00 того же преподавателя.
- **Действия:** создать второе занятие.
- **Ожидание:** рекомендация — разрешить, трактуя интервал как `[start, end)`; FR-07 этого не определяет. Не помечать прохождение до утверждения.

### A-SCH-13 — неизвестный идентификатор занятия (дополнение)
- **Техника / требование:** класс несуществующей сущности; HTTP error contract реализации, FR-07 scope.
- **Состояние и вход:** чистая БД; `lesson_id=999999` для GET/PATCH/DELETE и переноса; PATCH со статусом `scheduled`, темой `Алгебра`, пустыми материалами и заметкой.
- **Действия:** выполнить запросы к `/api/lessons/{id}` и `/api/mock/lessons/{id}/reschedule`.
- **Ожидание:** GET и DELETE — 404; PATCH и reschedule — 422 с `Занятие не найдено`; в БД нет новых занятий. Коды/формат — зафиксированный текущий API-контракт, не отдельный критерий FR-07.

### A-SCH-14 — недопустимое обновление занятия
- **Техника / требование:** класс невалидного поля и класса невалидной структуры / FR-07 (тема обязательна); API contract (materials list).
- **Состояние и вход:** занятие со `topic=Алгебра`, `status=scheduled`; отдельно отправить пустую тему и `materials="not-a-list"`.
- **Действия:** PATCH `/api/lessons/{id}`, затем проверить новую DB session.
- **Ожидание:** 422 с соответствующей ошибкой; исходные тема и статус не изменены. Неверный тип materials проверяет API-валидацию, а не новое бизнес-правило.

### A-SCH-15 — отсутствует обязательная тема при создании
- **Техника / требование:** класс недостающего поля / FR-07.
- **Состояние и вход:** корректные данные занятия, поле `topic` отсутствует.
- **Действия:** POST `/api/lessons`.
- **Ожидание:** 422, занятие в БД не появляется.

### A-SCH-16 — перенос без времени начала
- **Техника / требование:** класс недопустимого запроса переноса / FR-07.
- **Состояние и вход:** занятие 09:00–10:00; payload содержит дату переноса без `start`.
- **Действия:** POST reschedule и прочитать исходную запись новой DB session.
- **Ожидание:** 422; дата и время занятия не меняются.

### A-SCH-17 — удаление существующего занятия
- **Техника / требование:** изменение состояния / существующий API.
- **Состояние и вход:** собственное созданное синтетическое занятие.
- **Действия:** DELETE `/api/lessons/{id}`; затем проверить БД и GET.
- **Ожидание:** успех; запись удалена, дальнейший GET возвращает 404. Не считать это отдельным критерием FR-07.

### A-SCH-18 — совместимый маршрут создания расписания
- **Техника / требование:** эквивалентные валидные/незаполненные payload / маршрут, используемый `dashboard.js`.
- **Состояние и вход:** `/api/mock/lesson`; проверить корректный payload, пустую тему и top-level JSON, который не является объектом.
- **Действия:** POST каждого варианта, проверить response и БД.
- **Ожидание:** валидное занятие сохранено и возвращено в `entity`; пустое поле даёт 422 без записи; не-объектный payload даёт 422 «Некорректные данные» без записи.

### A-SCH-19 — ошибка ограничения БД при commit
- **Техника / требование:** error path / целостность FR-16 и существующий DB CHECK `ck_lessons_status`.
- **Состояние и вход:** отдельная тестовая SQLite; тестовый SQLAlchemy `before_commit` добавляет синтетическую Lesson с запрещённым статусом, чтобы БД реально отклонила commit.
- **Действия:** одновременно создать валидное занятие через API; проверить response и БД.
- **Ожидание:** integrity error преобразуется в 422, транзакция откатывается и валидная запись тоже не сохраняется. Это инъекция DB-ошибки только в тестовой БД, не production-логика.

### A-SCH-20 — страница расписания отображает событие
- **Техника / требование:** end-to-end smoke существующей страницы расписания и передаваемого календарного события.
- **Состояние и вход:** создать занятие через API для собственного активного синтетического ученика.
- **Действия:** GET `/schedule`.
- **Ожидание:** 200; шаблон содержит календарный контейнер и событие `lesson-{id}` созданного занятия. Тест проверяет интеграцию страницы с календарным сервисом, не UI-рендеринг JavaScript.
