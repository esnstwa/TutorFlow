# TutorFlow

TutorFlow — веб-платформа для взаимодействия частных репетиторов и учеников.

## Architecture

Технические решения и границы модулей описаны в [docs/architecture.md](docs/architecture.md).

## Локальный запуск

Создайте `.env` из `.env.example`, только если своего `.env` ещё нет. Для локального HTTP используется `APP_ENV=development`; Compose по умолчанию публикует сайт только на `127.0.0.1:8000`. Сборка образа передаёт в него SHA исходного состояния; суффикс `-dirty` означает незакоммиченные изменения затронутых файлов.

```bash
python scripts/build_component.py image
docker compose up -d
docker compose exec -T web alembic upgrade head
```

Демонстрационные данные загружаются отдельно, только в development-БД:

```bash
docker compose exec -T web python -m app.seed
```

Не запускайте seed при обычном обновлении заполненной БД. Перед миграцией сделайте резервную копию БД, а перед пересозданием web-контейнера — также `/app/var`: uploads пока не подключены к постоянному volume.

## Регистрация и авторизация

- `/register` создаёт реального `User` преподавателя или ученика через `create_user` и существующее хэширование пароля.
- `/login` принимает email и пароль. Роли направляются в `/dashboard` и `/student/homework` соответственно.
- Cookie `tutorflow_session`: HttpOnly, SameSite=Lax, Path=/; в БД только SHA-256 токена серверной сессии. Без «Запомнить» сессия действует 12 часов, с ним — 30 дней.
- `APP_ENV=production` включает Secure cookie и требует HTTPS. Без явного окружения настройки приложения по умолчанию production. Для reverse proxy требуется согласованное HTTPS-origin.
- `/api/auth/me` возвращает текущего пользователя и CSRF-токен. Защищённые изменяющие API-запросы требуют `X-CSRF-Token`; форма выхода передаёт `csrf_token`. JSON login/register требуют same-origin и `X-TutorFlow-Request: auth` при отсутствии Origin.
- POST `/logout` завершает серверную сессию и возвращает на `/login`.
- Development fallback и `request.state.user` больше не предоставляют доступ. Старые параметры `DEV_*` сохранены для совместимости конфигурации, но не используются для входа.
- Seed-аккаунты имеют заведомо нерабочие хэши и не получают общий пароль автоматически. Их данные сохраняются, но новый пользователь не получает чужую историю. Пароли существующих аккаунтов не сбрасываются при миграции.
- Восстановление пароля и подтверждение email письмом пока не реализованы; интерфейс честно сообщает об отсутствии recovery.

## Жизненный цикл ученика

`Student` — запись преподавателя, `User` — аккаунт. Совпадение email не связывает их автоматически.

1. Преподаватель добавляет ученика с его почтой.
2. В профиле нажимает «Пригласить» и вручную передаёт ссылку. Письмо автоматически не отправляется.
3. Ученик регистрируется или входит с указанной почтой и явно принимает приглашение.

Ссылка одноразовая, действует 7 дней, в БД только SHA-256 токена. Повторное приглашение, смена почты и архивирование отзывают прежние ссылки. Статусы: «Не связан», «Приглашен», «Связан».

Профиль можно редактировать и архивировать. `DELETE /api/students/{id}` также архивирует, а не удаляет историю. Архив доступен из списка учеников; новые назначения архивированным ученикам запрещены, старые задания и ответы остаются. Восстановление записи предусмотрено API `POST /api/students/{id}/restore` и не оживляет прежние приглашения.

## Проверки

```bash
uv sync --locked --extra dev
uv run --locked --no-sync python -m pytest -q
uv run --locked --no-sync python scripts/check_component.py
node --test tests/auth-wizard.test.cjs tests/student-lifecycle.test.cjs
node tests/test_session_fetch.cjs
docker compose exec -T web alembic current
docker compose exec -T web alembic check
```

Pytest использует отдельную SQLite-БД и не заменяет проверку миграций и конкуренции на PostgreSQL. `/health` проверяет приложение, а не БД.

## Минимальный компонент и wheel

Для smoke-сценария ПЗ №1 компонент — пакет приложения с его шаблонами и статическими ресурсами, а не отдельный микросервис. Wheel собирается только из отслеживаемых файлов `app/` и `pyproject.toml`; он содержит `app/build-info.json` с SHA сборки, но не включает корневой каталог миграций, тесты, документацию и локальные файлы. Миграции нужны только для развёртывания полной версии с БД, не для `GET /health` и CSS-сценария.

```bash
python scripts/build_component.py wheel --out-dir <вне-репозитория> --work-dir <вне-репозитория>
python scripts/verify_wheel_runtime.py --wheel <путь-к-wheel> --expected-sha <SHA-сборки>
```

Проверка устанавливает wheel вне checkout, внутри отдельного постороннего Git-репозитория, и выполняет `GET /health` плюс запрос CSS расписания. Для установленного wheel SHA берётся только из packaged `app/build-info.json`; исходный checkout определяет SHA через `git rev-parse HEAD`. `/health` сохраняет прежний контракт `{"status":"ok"}` и не запускает диагностику/Git на каждый запрос; версия и SHA записываются в событиях запуска/остановки приложения и доступны в CLI runtime-диагностики. Инструкции и ограничения доказательств — в [материалах ПЗ №1 МДК.01.04](docs/mdk01.04/pz01/README.md).
